Auditing an Inherited Excel Model with AI: Hardcodes, Broken Links and Inconsistent Formulas

Review a forecast model you didn't build: use Claude Code to list hardcodes, broken links, hidden sheets and unit errors by cell, without editing it.

Sooner or later every FP&A analyst and controller inherits a model. It is called something like Forecast_v19_FINAL2.xlsx, the person who built it has moved on, and it is due at the bank or the board next week. You need to know whether its mechanics can be trusted before anyone relies on the output.

Checking every formula by hand is slow. AI can do the reading. The method below has an AI tool write a script that reads every formula, lists each problem by sheet and cell, and leaves the model untouched. You then decide what gets fixed.

The rule: let the AI write the script, not read the data

The tool here is Claude Code, Anthropic's AI tool that works on files on your own computer (it needs a paid Claude plan). Instead of reading the workbook into a chat, it writes a short Python script that runs on your laptop and reads the formulas, then shows you the results. The model mostly sees labels, a few formulas and the script's findings, not the whole file.

That reduces what is sent; it does not make it zero, because the findings quote real cells and labels. Copy the model into a clean job folder with nothing else in it, start Claude Code there, and read each permission prompt before you approve it.

Step 1: Map the workbook before reading formulas

This step often finds problems before a single formula is read: a hidden sheet labeled "do not use" that something still refers to, a link to a workbook that isn't in the folder, a cover note saying one sheet is in thousands while the summary is in dollars. What is hidden, what is linked, and what units each sheet is in: ask those three questions of any inherited model.

Step 2: The formula review

This prompt is a model-review checklist, written out as instructions:

Two parts of this prompt matter more than they look. Rule 1 keeps formulas as text: a review file whose formula column holds live formulas recalculates, breaks or points back at the model, and text is evidence where a live formula is not. And asking for a plain-English build-up of revenue tests whether the review understood the model's flow, not just its cells.

What each check catches:

  • Hardcodes in formula rows. A 2028 revenue cell typed as a number in a row of formulas. It looks right today and never moves when an input changes.
  • Inconsistent formulas. One cell in a row pointing at the wrong growth rate, which is easy to miss in a row of similar formulas.
  • Numbers inside formulas. =F7*1.03 gives the right answer today and the wrong one when the price-increase input changes.
  • Short SUM ranges. A total that stops one row above the block, leaving out a line such as software costs.
  • External links. A rate pulled from a file nobody has.
  • Hidden sheets and rows. An old assumption still feeding revenue, or an unexplained manual adjustment in a hidden row.
  • Circular references. Interest, net income and debt depending on each other, sometimes deliberately.
  • Unit mismatches. A sheet in thousands feeding a summary in dollars. This one looks like a normal formula and can change EBITDA by more than everything else on the list combined.

Step 3: Rank by what the reader would see

Rank by effect on the output, not by how odd a cell looks. A #REF! on a ratio nobody uses looks alarming and changes nothing; a units slip changes every line below it. Each item should end in a decision, not a fix: is the typed figure a deliberate override, is the old premium still policy, what is the unexplained adjustment? Those answers come from people, not from a script.

How to check the result

  • Every named cell, in Excel. Go to each cell on the Issues sheet (Ctrl+G) and look. Formulas, Show Formulas makes breaks in a row's pattern easy to spot.
  • The model is unchanged. Its date modified should not have moved during the review.
  • The Formula column is text. Click a few cells on the Issues sheet; you should see the formula as text, not a calculated value.
  • The dollar effects. If the model has never been calculated in Excel, the script may have worked out impacts in Python. Check the two largest yourself.
  • Cell references in the chat. The chat can name the wrong column even when the file is right. Use the references in Model_Review.xlsx, not the conversation.
  • What it was not asked to check. Logic, not just mechanics: how tax behaves on a loss, how debt is repaid, whether the growth rates are sensible. The review covers what the prompt listed and little more.

What goes in the review file

Keep the model exactly as received, with who sent it and when; review_model.py, Model_Review.xlsx and the summary, dated; the decisions and who made them; then the new version, the fix log, and a rerun of the review script on it showing what is left and why.

Limits

The script finds mechanical problems: hardcodes, broken links, inconsistent formulas, hidden content, unit mismatches. It does not tell you whether the assumptions are reasonable or the business logic is sound, and a circular reference may be a deliberate, documented loop rather than an error. Treat its ranking as a starting point for a conversation with the CFO, not the conclusion. Results also vary between runs and versions of the tool, which is why every finding gets checked in Excel before it goes in a memo.
